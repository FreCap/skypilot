# Managed Jobs Registration Repository

_Created: 2026-08-11_

## Problems

`sky/jobs/state.py` is a 2,922-line stable facade that still implements both
constructors for the initial `job_info` row alongside scheduler transitions,
controller ownership, recovery, cancellation, terminalization, and cleanup.
The constructors have different transport callers but one persistence
contract: create an inactive job with either a database-assigned ID or a
controller-preallocated ID, using the active database dialect, one insert, and
one commit.

The seam must stop at initial registration. Creating task rows with
`set_pending`, changing schedule state, and controller recovery all have
separate lifecycle ordering, event, retry, and ownership-fencing concerns.
Sharing `job_info` is not enough reason to move those operations.

## Goals

Move the complete initial-row registration protocol to one low-state
repository while preserving `sky.jobs.state` as the public facade. Preserve
public import paths, function names and signatures, module and pickle identity,
generated-code compatibility, SQLite and PostgreSQL behavior, row contents,
ID allocation, exception behavior, insert and commit counts, and caller
behavior. Preserve the historical `sky.jobs.state.sqlite` and `.postgresql`
dialect-module exports even though the extracted implementation owns their
production use.

No schema, serialized format, CLI output, API version, remote command,
lifecycle order, or user-visible behavior changes.

## Background and Responsibility Map

### Database-assigned registration

`set_job_info_without_job_id` is called by the API-server jobs service,
consolidation-mode submission, the skylet service, and compatibility code
generated by `JobLibCodeGen`. It depends on the synchronous database manager,
SQLAlchemy dialect-specific inserts, and the `job_info` schema. It owns the
allocation and durable contents of one initial row, including workspace,
entrypoint, pool identity, user identity, execution mode, batch mode, and the
optional file-mount blob reference. Its failure modes are an unsupported
dialect, a failed insert or commit, a missing generated ID, or an incorrectly
initialized field. It is submission-latency-sensitive and must remain one
insert and one commit. It changes when API-server, consolidation, or skylet
submission adds initial metadata.

### Preallocated-ID registration

`set_job_info` is called only through managed-job controller code generated by
`ManagedJobCodeGen`, including compatibility gates for old controller
versions. It uses the same synchronous database manager, dialect-specific
insert, table, initial schedule state, and commit contract, but persists a
caller-provided job ID and omits the newer file-mount reference. Its failure
modes are duplicate/preexisting IDs, generated-code signature drift, an
unsupported dialect, or partial initialization. It is controller-start
latency-sensitive and must remain one insert and one commit. It changes when
the generated controller protocol or its version gates change.

### Retained lifecycle persistence

`sky.jobs.state` retains task-row creation, scheduler transitions, controller
generation fences, cancellation, recovery, terminalization, cleanup, status
queries, and event recording. Those callers depend on task rows, state-machine
invariants, retry policy, locks, outer-controller ownership, and destructive
cleanup ordering. Their failure modes and change cadence are materially
different from constructing an inactive initial row.

## Solution

### v0: Characterize the public protocol

Add focused tests against the unmodified facade for both constructors. Prove
signatures, names, historical module and pickle lookup, complete SQLite row
contents, database-assigned and explicit IDs, inactive initial state, one
insert, one commit, duplicate-ID failure, and PostgreSQL statement shape.

### v1: Extract the registration repository

Create `sky/jobs/state_job_registration.py` containing the exact two
implementations. Use `state_storage.db_manager`, `state_schema.job_info_table`,
and `status_types.ManagedJobScheduleState` directly. Set each function's public
identity to `sky.jobs.state`, then bind direct aliases in the facade. Direct
aliases preserve imports and serialization without another runtime frame.
Retain explicit dialect-module imports in the facade as compatibility exports;
existing state tests and external debugging code may access them directly.

Keep the two small implementations explicit instead of introducing a shared
private builder. Their return protocols differ by dialect and ID ownership;
deduplicating a few lines would make the characterization less direct and
would mix PostgreSQL `RETURNING` behavior into the preallocated path.

Rollback is a source-only revert because no migration or data rewrite occurs.

## Alternatives Considered

Leaving both constructors in place avoids a new module, but retains one
complete and frequently changing transport-facing persistence protocol inside
the lifecycle facade. The two constructors already evolve together as initial
metadata fields are added, while their callers and failure modes remain
separate from lifecycle transitions.

Moving only `set_job_info_without_job_id` was rejected because it would leave
the other constructor for the same initial-row invariant buried at the opposite
end of the facade. Moving `set_pending` was rejected because task registration
records a lifecycle event and owns a different table and ordering contract.

Wrappers were rejected because they add frames and weaken exact public
identity. A class, protocol, factory, builder, strategy, registry, or dependency
injection layer was rejected because construction is one statement, there is
no staged assembly or second storage implementation, and plain functions match
the existing persistence boundary.
